The registry contains the same provider names as the tracked Python source revision. Native
adapters handle services whose SDK or protocol needs translation, while a data-driven adapter
handles OpenAI-compatible endpoints. The table below is generated from
`AnyLLM.getAllProviderMetadata()` during development and checked for drift in CI.

## Read metadata at runtime

```ts
import { AnyLLM } from "any-llm-ts";

const names = AnyLLM.getSupportedProviders();
const openai = AnyLLM.getProviderMetadata("openai");
const everyProvider = AnyLLM.getAllProviderMetadata();
```

Each `ProviderMetadata` object includes:

- the normalized provider `name`
- the default `apiBase`, when one exists
- the conventional `envApiKey` and `envApiBase`
- whether an API key is required
- the provider's documentation URL
- conservative operation and feature capabilities
- the `verified` or `community` integration tier
- whether `promptCacheKey` is supported, forwarded, or rejected

## Adapter categories

| Adapter                      | Providers                                                                                               |
| ---------------------------- | ------------------------------------------------------------------------------------------------------- |
| OpenAI and OpenAI-compatible | `openai`, `azureopenai`, plus compatible registry rows                                                  |
| Anthropic                    | `anthropic`, `azureanthropic`, `vertexaianthropic`                                                      |
| Google Gen AI                | `gemini`, `vertexai`                                                                                    |
| AWS                          | `bedrock`, `sagemaker`                                                                                  |
| Other native integrations    | `azure`, `cohere`, `github`, `huggingface`, `meta`, `mistral`, `otari`, `together`, `voyage`, `watsonx` |

Provider registration indicates API compatibility. It is not a claim that every provider, model,
region, account tier, and operation is continuously tested with live credentials.

The parity manifest records the Python source commit, provider names, operations, capability
matrix, and verified set. CI compares that manifest with the runtime registry so future source
updates produce an explicit, reviewable parity gap.
